Responde unas preguntas.
Obtén un proyecto que tu agente entiende.

agent-kit prepara un proyecto para desarrollo dirigido por agentes: las reglas las aplican hooks en vez de texto, el contexto que se carga en cada sesión se mantiene pequeño, el trabajo se retoma donde quedó y cada spec queda trazada a tests.

Sin dependencias en ejecución · Node ≥ 20.11 · cada versión se prueba en Claude Code real

Lo que falla es el arnés, no el modelo

Los agentes leen lo que cargas en cada sesión y olvidan todo lo demás. Sin un arnés, los proyectos caen en los mismos problemas:

Contexto carísimo

Un ERP real en producción cargaba ~22.900 tokens de AGENTS.md y memoria en cada sesión, antes de hacer una sola pregunta.

Reglas escritas en prosa

"Nunca hagas commit en main" en un Markdown es una sugerencia. Un hook que bloquea el comando es una regla.

Scripts reescritos una y otra vez

Los scripts escritos en /tmp no se encuentran la próxima vez, así que se reescriben: sin documentar y sin tests.

Sesiones que olvidan

Una sesión nueva no sabe qué spec quedó a medias, qué tarea seguía ni qué cambió.

Cómo funciona

1

Respondes preguntas fijas

Tipo de proyecto (monorepo de app, sitio de contenido, proyecto existente o en blanco), nivel técnico, idioma de respuesta, método (SDD o SDD + TDD), convención de commits y flujo de git. Nada se adivina.

2

Obtienes la capa del agente

Un bloque corto en AGENTS.md, agent-kit.json, configuración aplicada, .knowledge/, work/, scripts/ y el plugin, activado desde su marketplace.

3

Cada sesión empieza bien

Un hook inyecta el perfil, dónde quedó la última sesión, el trabajo activo con su siguiente tarea y un índice de conocimiento de una línea por entrada: unos 1.300 tokens.

Tres carriles, dos métodos

El agente dice en qué carril trabaja antes de empezar, para que puedas corregir a tiempo. El método que elegiste decide cuánta prueba necesita cada cambio.

Responder

Preguntas y exploración. Solo lectura.

Vía rápida

Cambios pequeños (≤ 3 archivos, sin cambios de esquema, permisos ni dinero). Un archivo de feature con tareas y evidencia; un cambio de comportamiento también actualiza su spec viva.

Spec

Todo lo demás, como un cambio: propuesta + specs delta → tu aprobación → plan → tareas → implementación → verificación de cada escenario → fusión en las specs vivas.

MétodoQué exige
SDDCada escenario se prueba con un test o una comprobación reproducible.
SDD + TDDUn test que falla antes de cada cambio de comportamiento (rojo → verde → refactor, casos elegidos con ZOMBIES). Los tests empiezan con el escenario que prueban (auth.R2.S2); preflight bloquea la lógica sin tests y los cambios terminados con escenarios sin probar o sin fusionar.

Specs vivas, una notación, QA que las sigue

SDD anclado a specs: las specs vivas en work/specs/<capacidad>/ dicen cómo se comporta el sistema hoy. Cada cambio trae un delta que se fusiona en ellas, y cada paso usa una notación estándar.

Deltas fusionados por un script

Un cambio AÑADE, MODIFICA o ELIMINA requisitos. specs.mjs merge los aplica todos o ninguno y retira los ids eliminados, que nunca se reutilizan: tests, pasadas de QA y fixtures siempre apuntan al comportamiento correcto.

Checklist de QA

Generado desde las specs vivas, nunca editado a mano: los pasos, la etiqueta ZOMBIES y el fixture detrás de cada escenario. Una página sin conexión registra pass / fail / blocked y exporta la pasada.

Datos de prueba que no llegan a producción

Los proyectos con Supabase reciben seed.sql y purge.sql: una transacción cada uno, creados con las RPCs de la app, filas marcadas TEST_. Ambos se niegan a correr salvo que la tabla _env diga dev, test o staging. Opcional al instalar.

11 skills, cargadas solo cuando hacen falta

Hasta que la tarea la necesita, de cada skill solo se carga su descripción; además, una skill de stack por plantilla, instalada solo en los proyectos que la usan. Las descripciones están probadas: cada skill se activa con una petición realista y ninguna se carga con preguntas que no tienen que ver, en haiku y en sonnet.

Garantías que se aplican, no que se piden

Cuatro hooks y unos pocos scripts hacen las comprobaciones. Fuera de los proyectos de agent-kit no hacen nada y tardan 70–100 ms cada uno.

Guardia de git

Aplica el flujo de git que elegiste (solo lectura, trunk o ramas + PR), incluso a través de bash -c, eval, $( ) y alias de git. Valida los mensajes de commit antes de ejecutarlos.

Preflight

Antes de un merge: migraciones por aplicar o editadas por error, variables de entorno y dependencias nuevas, posibles secretos, restos de depuración, permisos a los roles del navegador, scripts sin documentar, lógica sin tests, criterios sin probar.

Retomar

Un punto de control tras cada turno; la siguiente sesión empieza sabiendo dónde quedó la anterior y la siguiente tarea de cada trabajo activo.

Aviso de scripts

Un script escrito donde se va a perder (/tmp, la raíz del proyecto) recibe un aviso para buscar, guardar y documentar.

  • Nunca force-push, reset --hard, clean -f ni --no-verify desde un agente.
  • Nunca un commit en main en un proyecto de ramas + PR.
  • Ninguna escritura de git en un proyecto de solo lectura: el agente te da el comando exacto.

Conocimiento que sigue siendo barato de cargar

Un concepto por archivo Markdown, enlazados con [[nombre]], con un index.md y un log.md por carpeta: la estructura del Open Knowledge Format. Solo se carga el resumen de una línea de cada entrada; los agentes abren archivos cuando los necesitan o buscan con un script.

Empieza desde un stack, o trae el tuyo

Monorepo de app

Nuxt 4 + shadcn-vue + Tailwind v4 + Supabase: sitio público, SPA con capa de servidor y autenticación (login con límite de intentos, sesión restaurada, protección de rutas), sitio de ayuda, UI y esquemas Zod compartidos, CI.

Sitio de contenido

Un sitio Nuxt donde cada archivo Markdown es una página, pensado para personas no técnicas, con un agente que habla en lenguaje sencillo y una guía en español.

Proyecto existente

Solo la capa del agente: tu AGENTS.md se conserva y recibe un bloque gestionado; adopt te ayuda a adelgazarlo.

Empezar

bash 
npx @razcue/agent-kit init mi-proyecto   # responde las preguntas
cd mi-proyecto && npm install && claude    # confía en la carpeta, acepta el plugin
npx @razcue/agent-kit doctor              # comprueba la configuración

Después: agent-kit upgrade pregunta solo lo nuevo y muestra qué cambió; agent-kit uninstall quita solo lo que añadió el kit. Si Claude Code no ofrece el plugin solo, ejecuta /plugin marketplace add razcue/agent-kit y luego /plugin install agent-kit@agent-kit.
