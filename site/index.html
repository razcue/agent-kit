The harness, not the model, is what goes wrong

Agents read whatever you load into every session — and forget everything else. Without a harness, projects drift into the same failures:

Context that costs a fortune

A real production ERP loaded ~22,900 tokens of AGENTS.md and memory on every session, before a single question was asked.

Rules written as prose

"Never commit on main" in a Markdown file is a suggestion. A hook that blocks the command is a rule.

Scripts rebuilt again and again

Helpers written in /tmp are invisible next time, so they get rewritten — undocumented, untested.

Sessions that forget

A new session doesn't know which spec was half-done, which task was next, or what changed.

How it works

1

Answer fixed questions

Setup (app monorepo, content site, existing or blank project), technical level, reply language, method (SDD or SDD + TDD), commit convention, git flow. Nothing is inferred.

2

Get the agent layer

A short AGENTS.md block, agent-kit.json, enforced settings, .knowledge/, work/, scripts/ — and the plugin, enabled from its marketplace.

3

Every session starts right

A hook injects the profile, where the last session stopped, the active work with its next task, and a one-line-per-entry knowledge index — about 1.3k tokens.

Three lanes, two methods

The agent names the lane before it starts, so you can redirect early. The method you chose decides how much proof each change needs.

Answer

Questions and exploration. Read-only.

Fast-track

Small changes (≤ 3 files, no schema, permission or money change). One feature file with tasks and evidence; a behaviour change also updates its living spec.

Spec

Everything else, as a change: proposal + delta specs → your approval → plan → tasks → implement → verify every scenario → merge into the living specs.

MethodWhat it requires
SDDEach scenario is proven by a test or a reproducible check.
SDD + TDDA failing test before every behaviour change (red → green → refactor, cases chosen with ZOMBIES). Tests start with the scenario they prove (auth.R2.S2); preflight blocks untested logic and finished changes with unproven or unmerged scenarios.

Living specs, one notation, QA that follows

Spec-anchored SDD: the living specs in work/specs/<capability>/ say how the system behaves now. Each change carries a delta that merges into them, and every step uses one standard notation.

Deltas, merged by a script

A change ADDs, MODIFIEs or REMOVEs requirements. specs.mjs merge applies them all or nothing and retires removed ids, which are never reused, so tests, QA runs and fixtures always point to the right behaviour.

QA checklist

Generated from the living specs, never edited by hand: the steps, the ZOMBIES tag and the fixture behind each scenario. An offline page records pass / fail / blocked and exports a run file.

Test data that can't hit production

Supabase projects get seed.sql and purge.sql: one transaction each, created through the app's RPCs, rows marked TEST_. Both refuse to run unless the _env table says dev, test or staging. Optional at setup.

11 skills, loaded only when needed

Each skill's description is all that loads until the task needs it, plus one stack skill per template, installed only in projects that use it. Descriptions are tested: every skill triggers on a realistic request, and none load on unrelated questions — on haiku and on sonnet.

Guardrails that are enforced, not requested

Four hooks and a few scripts do the checking. They are silent outside agent-kit projects and take 70–100 ms each.

Git guard

Applies the git flow you chose — read-only, trunk, or branches + PRs — even through bash -c, eval, $( ) and git aliases. Validates commit messages before they run.

Preflight

Before a merge: migrations to apply or wrongly edited, new env vars and dependencies, possible secrets, debug leftovers, grants to the browser roles, undocumented scripts, untested logic, unproven criteria.

Resume

A checkpoint after every turn; the next session starts with where the last one stopped and the next task of each active piece of work.

Script reminder

A script written where it will be lost (/tmp, the project root) gets a reminder to search, keep and document it.

  • Never force-push, reset --hard, clean -f or --no-verify from an agent.
  • Never commit on main in a branches + PR project.
  • Never run git writes at all in a read-only project — the agent hands you the exact command.

Knowledge that stays cheap to load

One concept per Markdown file, linked with [[name]], with an index.md and a log.md per folder — the Open Knowledge Format layout. Only each entry's one-line summary is loaded; agents open files on demand or search with a script.

Get started

bash 
npx @razcue/agent-kit init my-project   # answer the questions
cd my-project && npm install && claude    # trust the folder, accept the plugin
npx @razcue/agent-kit doctor             # check the setup

Later: agent-kit upgrade asks only new questions and shows what changed; agent-kit uninstall removes only what the kit added. If the plugin isn't offered automatically, run /plugin marketplace add razcue/agent-kit then /plugin install agent-kit@agent-kit in Claude Code.
